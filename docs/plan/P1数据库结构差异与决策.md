当前 schema 有 7 张表：认证的 user/session/account/verification，以及 conversation/message/generation_run。消息完整内容保存在 message.payload；生成任务已有原始 usage JSON 字段。中文方案中的 attachment、attachment_provider_ref、message_attachment、usage_record、cleanup_job 尚未在该 schema 声明，不能把设计表当成已创建。

## 2. 决策：附件及清理表暂缓落库

附件功能当前明确拒绝，尚未选定对象存储、业务限额、保留期及删除政策。仅创建空表不能满足上传归属、供应商补偿、引用计数与清理验收，还会过早固定生命周期。因此将以下表的落库与功能一并安排到 P5，而非为勾选 P1 建空表：

| 表 | 最小安全设计 | 落库前条件 |
| --- | --- | --- |
| attachment | 业务 ID、owner、MIME/大小/hash、私有 storage key、上传状态、软删时间；不存 Blob 或签名下载 URL | 存储选型、大小/类型配额 |
| attachment_provider_ref | attachment、provider、非秘密 credential scope、remote file ID、状态；三者唯一 | 明确供应商生命周期和重传策略 |
| message_attachment | message、attachment、position；唯一引用/顺序约束；跨用户引用拒绝 | 服务端归属校验、复用附件语义 |
| cleanup_job | kind/resource、幂等键、状态、attempts、重试时间、lease、脱敏错误 | 保留期、最后引用解除规则、执行器与失败补偿 |

不创建存储桶、不启用删除任务，不因会话软删除立即删除文件。需用户决定：R2 或 Neon Object Storage；容量/类型限制；附件保留与删除政策。旧附件永不进入该流程。

## 3. 用量可先做，不依赖附件服务

当前 `generation_run.usage` 适合本地调试，不等于完成账本：缺少 completeness、规范化 token 字段及预算预留/结算状态。`generation.ts` 最终写入 `reply.usage`；续写沿用同一个 assistant，因此必须额外证明每次 attempt 用量只来自本次上游响应，不能以整条消息最终 usage 推定每次任务实际用量。当前未完成此验收。

建议最小落地方案：

1. 新建 usage_record，以 generation_id 为主键或唯一键，FK 指向 generation_run。owner 从生成记录推导，不信任客户端传入。
2. 原始 raw_usage 可空；input/cached_input/output_tokens 为可空非负 bigint，tool_usage 为 JSON。未知不写 0，缺失字段不补算。
3. completeness 限制为 unknown/partial/complete。仅在确定收到供应商终止标志且所需用量字段齐全时 complete；取消、断流不推定完整。
4. 每个新 generation attempt 在事务内建 unknown 记录；最终状态及账本原子提交，generation_id 唯一确保重试不重复入账。保留原 generation_run.usage 仅为兼容字段，明确账本为新数据的权威来源。
5. 续写开始时另建 attempt-local usage 累积器，不从上次 reply.usage 初始化；供应商累计字段采用覆盖语义，不将 start/delta 重复相加。
6. 不回填旧聊天或旧生成记录。账本上线前记录显式归为“未纳入新账本”，不伪造历史准确性。价格估算及用户额度另属 P6，不混入 token 账本。

验收至少覆盖：同一任务重复落账、同键不同请求、多次续写、缺失 usage、取消/错误、终态事务失败回滚。仅有表而未接入这些写入路径，不算实现完成。
